## Autonomous Katstrology delivery

Standing user instruction: `kat-autonomous-delivery-20261110-v1`. This authority is specific to Katstrology and already requested work, including automatic person memory and the Luna default. It does not change other projects or global agent policies.

- Carry agreed work through implementation, independent code/UI review, remediation, qualification, Git publication/PR/required checks, protected merge, guarded deployment and serving verification without asking the user to start each stage or approve deployment again. This is the user's direct standing delivery authorization, not an inference from silence.
- The user's standing review selection is **fix all actionable in-scope findings**. Investigate and deduplicate findings, reject contradicted claims with evidence, and fix ordinary defects through the sole implementation owner. Preserve independent reviewers, exact-tip evidence and bounded re-verification. Do not silently defer a release blocker or replace independent review with self-review. No additional human fix-selection gate is required for ordinary findings.
- Keep routine engineering and delivery decisions out of the user's loop. Choose proportionate, reversible solutions within the agreed outcome; send a concise verified completion, not routine progress or approval requests.
- **Keep the user involved in material security/privacy matters.** Promptly report supported findings or changes involving authorization, consent, cross-account access, credentials, private-data exposure or weakened trust boundaries, with evidence, impact and the recommended response. Continue safe investigation and reversible local remediation, but do not ship a security-sensitive change, accept a security risk or weaken a protection without the user's specific direction.
- **Escalate migrations when a real data-integrity decision is needed.** Routine additive migrations may proceed only through the existing compatible native release lane with its required schema/preservation/snapshot checks. Stop for destructive or incompatible migrations, uncertain data semantics, restore/rollback of databases or journals, or any migration requiring an explicit native exception. Present the exact migration and consequence; never bypass a guard.
- **Ask for exact missing manual access only.** Use existing enrolled native access without exporting credentials. If server login/unlock or another manual step is required, state that prerequisite and let the user authenticate directly; never request a password/token in chat. Missing access is not a renewed deployment-approval request.
- Never bypass required CI, immutable source/image identities, ownership/admission fences, snapshot/deletion authority or native halt/recovery rules. Preserve failed attempts; no blind reruns, bare fence clearing or restoration of old databases/journals. A native halt requires evidence and a compatible, separately scoped recovery disposition, not a generic restart. Unrelated server/network/admin changes are outside ordinary app delivery.
- Deployment authorization does not authorize real-provider test conversations, private-account/fixture access, credential extraction, unrelated features or arbitrary paid traffic. These retain their existing exact-scope requirements. Existing explicitly authorized live checks remain limited to their approved scope.
